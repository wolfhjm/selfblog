# 事件、感受、洞察串联能力草稿

## 背景

当前系统已经有打卡、探索对话、候选收件箱、认知地图等基础能力，但结构化对象之间的连接还比较粗。

问题不是单纯缺少更多对象，而是事件、客观环境、当时感受、隐藏动机、后续洞察之间还没有被充分串联。尤其是“感受”不应该独立漂浮，它通常依附在某个具体事件、场景或解释方式上。

## 核心想法

### 1. 小事件需要拆得更细

一次打卡或一段对话里可能包含多个事件。现在 AI 提取时容易把一整段经历概括成一条候选，粒度偏粗。

更理想的拆分方式是：

- 先拆客观发生了什么
- 再拆当时的身体/情绪反应
- 再拆用户对事件的解释
- 再拆可能隐藏的需求、恐惧、期待或冲突
- 最后才提炼洞察、经验教训或原则草稿

事件不是为了“记流水账”，而是为了给后续洞察提供证据。

### 2. 感受不应作为完全独立对象

感受需要挂在事件、环境或解释上。例如：

- 事件：买的号突然不能用了
- 客观环境：上班时一直盯着额度，注意力被占用
- 感受：消耗、烦躁、不安
- 解释：好像自己又在浪费精力
- 隐藏东西：对失控、资源浪费、低效投入的敏感

所以“感受/反应”更像事件详情的一层，或者至少需要默认关联到某个事件。

### 3. 洞察需要带上下文证据

洞察不能只是一句抽象总结。每条洞察最好能回答：

- 它是在什么客观环境下出现的？
- 相关事件是什么？
- 当时真实感受是什么？
- 用户当时怎么解释这件事？
- 有没有隐藏的恐惧、需求、期待或自我保护？
- 这个洞察支持什么经验教训、规律或原则？

这样洞察才不会变成漂亮但无根的话。

### 4. 对话模式需要辅助发掘隐藏信息

当前对话更像自由陪伴和提炼。后续可以增加一种“结构化追问模式”，围绕某个事件或候选继续发掘：

- 这个事件里最具体的触发点是什么？
- 你当时身体有什么反应？
- 你第一反应给它贴了什么意义？
- 这件事让你害怕失去什么？
- 如果这个反应反复出现，它可能在保护你什么？
- 这件事和过去哪些经历相似？
- 如果要把它变成下次可用的经验，最小一句话是什么？

这类追问可以用于辅助写日记，也可以用于完善候选对象。

### 5. 自由对话里应能选择片段进一步分析

探索页可以保留自由聊天，但用户应能从一段对话中选择某条消息、某个候选、某个事件，进入“进一步分析/完善”。

可能的交互：

- 对候选点击“继续追问”
- 对事件点击“补充感受”
- 对洞察点击“寻找证据”
- 对经验教训点击“生成验证实验”
- 对一段日记点击“拆成事件链”

这样系统不是一次性提取，而是通过对话逐步把模糊体验打磨成结构。

## 可能的数据模型调整

### 事件详情层

可以考虑让 `case` 不只是标题和内容，而包含更多字段：

- `objective_context`：客观环境
- `event_detail`：发生了什么
- `body_signal`：身体信号
- `emotion`：情绪/感受
- `interpretation`：当时解释
- `hidden_need`：可能需求
- `hidden_fear`：可能恐惧
- `raw_evidence`：原始证据片段

也可以先不拆表，只把这些字段存在候选 `payload`，等模式稳定后再迁移到正式字段。

### 候选拆分策略

候选收件箱可以支持“候选组”或“事件链”：

- 一个来源对话生成一个候选组
- 组内包含多个事件
- 每个事件下挂感受、解释、洞察、经验教训
- 用户可以逐条确认，也可以先把整组放进收件箱

## 下一步建议

1. 调整 AI 候选提取 prompt，让它按“客观环境 -> 事件 -> 感受 -> 解释 -> 隐藏需求/恐惧 -> 洞察/教训”输出。
2. 先把结构化字段放进 `candidates.payload`，不急着改正式表。
3. 在候选收件箱里展示 payload 里的结构化细节。
4. 在候选卡片增加“继续分析”入口，基于候选内容开启一段追问对话。
5. 后续再决定是否把 `case`、`reaction`、`insight` 合并为更明确的“事件链”模型。

## 暂不确定

- 感受是否仍保留为独立认知对象，还是改成事件的字段。
- 事件链是否需要单独建表。
- 日记是否应该成为事件拆分的主要入口。
- 自由对话和结构化追问模式如何切换，避免界面变复杂。
